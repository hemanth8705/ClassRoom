Authorization Code flow · 8 steps
Why does Google send a code first, and not the token itself? Because the code comes back through the browser, where anyone could see it. On its own it's useless. The real tokens only travel on a private call from your server to Google, and that call needs your client secret. In the walkthrough, every step is tagged visible or private, so you can see which side of the line it's on.
STATE AND PKCE

state and code_challenge are public. Why send them?

Here's the tail end of the step 2 URL:

…&state=x7f3a9&code_challenge=E9Mel…&code_challenge_method=S256

Anyone watching the browser can read both values. Neither one hides anything, and neither is meant to. Each is a receipt: your server writes down its own copy before the user leaves, then checks what comes back against it. If you can compare a value with something the attacker can't touch, it's safe to send in the open.

state: did this login start here?

Before redirecting the user, your server makes a random string, stores it in that user's session, and puts the same string in the URL. Google hands it back untouched in step 4, and your callback compares the two.

The attack it stops is login CSRF. An attacker signs in to Google with their own account, stops at step 4, and keeps the callback link with their own code in it. Then they send that link to your user. If your callback accepts whatever code it's given, your user's session is now logged in as the attacker, and whatever they save next lands in the attacker's account. With state, the link carries a value your user's session never issued, so the callback rejects it. The attacker can read states all day. What they can't do is plant one in your user's session.

code_challenge: is this the app that started the login?

The code in step 4 passes through the browser, so it can leak: a browser extension, a proxy log, a referrer header. Whoever gets it first can swap it for tokens. A server-side app is partly covered, because the thief would also need your client secret. PKCE closes the rest of the gap, and current guidance recommends it for every client.

Before step 2, your server makes a random code_verifier and keeps it. It sends only the SHA-256 hash of that verifier, the code_challenge. Google stores the hash next to the code it issues. In step 5, your server sends the verifier itself. Google hashes it, compares the result with the stored challenge, and only then hands over tokens. A thief who has the code never saw the verifier, so the check fails. The challenge sitting in the URL doesn't help them either, because SHA-256 can't be run backwards.

# Step 2: keep the secret half, send only the public half
state     = secrets.token_urlsafe(16)                                   # also saved in the session
verifier  = secrets.token_urlsafe(32)                                   # saved in the session, never sent yet
challenge = b64url(hashlib.sha256(verifier.encode()).digest())          # goes in the URL

state ties the way back to the way out. code_challenge ties the token swap to the login that started it.

1. The fake callback link

An attacker signs in with their own Google account, grabs the callback link with their code in it, and sends it to your user. Your user clicks it.



2. The stolen code

A browser extension, or a leaked log, copies the code from the step 4 URL and races your app to Google.



WHAT YOU GET BACK

Google hands you three tokens

Step 6 returns one JSON body with three tokens in it:

{
  "access_token":  "ya29.a0AfH6…",
  "refresh_token": "1//0gLq…",
  "id_token":      "eyJhbGciOi…"
}

The access token calls APIs

Your server puts the access token in an Authorization header, and Google checks it, and the scopes behind it, before returning anything. It's short-lived on purpose: expires_in is 3599, so about an hour. If it leaks, the damage ends when it expires.

The refresh token keeps the user signed in

When the access token dies, your server sends the refresh token to Google's token endpoint and gets a new access token back. No user, no login screen. That convenience is the catch: a refresh token lasts until the user revokes it, so a stolen one means the attacker keeps minting access tokens. Encrypt it at rest, and never send it anywhere except that endpoint.

You only get one if you ask for it with access_type=offline. Google sends it the first time the user agrees. Add prompt=consent and you get a fresh one on every login.

The ID token says who logged in

The other two are about what your app may do. The ID token is about who just logged in. It's a signed JWT carrying the user's ID, email and name, and your backend reads it once, right after step 6. It isn't a key. Don't send it to an API, and don't use an access token to identify a user. The next section opens one up.

THE ID TOKEN

What's inside the ID token

The ID token is a JWT: three base64url chunks joined by dots, header.payload.signature. Select a chunk to see what it holds and how it decodes.

Change the payload, then verify

This token is signed with a throwaway key made in your browser, not Google's. The check is real: RS256, using your browser's crypto. Edit the email, then verify.

Decode it, then verify it

Decoding only reads the token. It proves nothing. Verification is what makes the claims trustworthy.

  1. Read kid from the header, and check alg is the algorithm you expect (RS256). Your code picks the algorithm, not the token.
  2. Fetch Google's public keys (JWKS) from googleapis.com/oauth2/v3/certs, and cache them.
  3. Take the key whose kid matches.
  4. Verify the signature over header.payload: the first two chunks, exactly as sent, joined by a dot.
  5. Only then check the claims: iss is Google, aud is your client_id, exp hasn't passed.

  BUILD · 1 OF 2
  
First, register your app with Google

  
Before any of this works, Google has to know your app exists. In the Google Cloud Console, open APIs & Services, then Credentials, and create an OAuth client ID (type: Web application). Microsoft and other platforms have the same step. You get two things back:

  

    
Client ID
Your app's public name. It goes in the login URL, and it's fine if everyone sees it.

    
Client secret
Your app's password. It stays on your server. It never goes in a URL, in the browser, or in Git.

  

  
Then you register a redirect URI, like http://localhost:3000/callback. It's the only address Google will send users back to. If a request doesn't match it exactly, Google refuses, so nobody can redirect your users' codes to their own site.


  
Scopes: what you're asking for

  
Scopes are the permissions your app asks for, and your app lists them in the login URL. Basic ones give you the user's name, email and profile photo. Privileged ones, like reading their calendar or Drive files, need an explicit yes from the user. Pick a few and see what your user would see.

Ask for the least you need. People click through a name-and-email screen. They close a "delete your Drive files" screen. Google also reviews apps that ask for sensitive or restricted scopes before the public can use them, so while you're testing, add your own account as a test user.

  ONE LAST THING
  
Authentication vs authorization

  
People mix these two up all the time. Here's the difference.

  

    
Authentication
Who are you? It's like showing your passport at the hotel desk.
In our flow, that's the ID token. This part is called OpenID Connect (OIDC), a thin layer on top of OAuth. It's what openid email profile switched on.

    
Authorization
What are you allowed to touch? It's like a keycard that only opens room 204.
In our flow, that's the access token and its scopes. This is OAuth itself.

  

  
"Continue with Google" does both at once. You prove who you are, and you decide what the app may do on your behalf.
